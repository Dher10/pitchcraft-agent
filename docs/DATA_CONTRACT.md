# Data contract — what the published file may say

Normative (decision D34). This contract defines what `public/data/pitchcraft-demo.json`, and every text that describes it, may contain. It does not replace `docs/DECISIONS.md`: where they differ, the decision wins and the difference is reported. QA (`docs/QA_PROTOCOL.md`) verifies compliance with this contract. A rule changes only through a new decision.

- **Annex A:** `docs/data-inventory.md`, the field-by-field inventory of the live payload at HEAD `043db03`. Its findings F1 to F13 (and F14 to F21, added below) are the **known violations** of this contract. Each was closed by the commit named in section 4. While they were open, `data_pipeline/known_violations.py` tolerated them and the generic checks of P0.15-D3 reported them; P0.15-D2.5c deleted that table, so every violation reported by the publication checks stops the file (`tests/test_no_tolerance.py` guards that behavior). This does not prove that those checks detect every possible source inconsistency or frontend claim; QA5 demonstrated that distinction, and P0.16 adds the corresponding source/component regressions.
- **Scope of "published":** every field of the JSON file, whether or not a component renders it, and every text that describes the file: agent text, generator text (workflow, metadata, archive labels), frontend text and workflow text.
- **Words used.** A *field* is a path in the file. A *group of figures* is a set of fields that come from one source with one scope (section 2, rule 3). An *unavailable state* is the explicit way a field says "no value": `null` for a scalar, `[]` for a list, `{}` for a map, and the documented sentinel for the few fields that are text by type (`"N/A"` for `season_summary.era`, `whip`, `innings`; `"Not available"` for `primary_pitch` and `putaway_pitch`). The sentinels are listed in the manifest of P0.15-D3; none may be a number.

## 1. Where a value comes from

Every published field is exactly one of:

| Kind | Meaning | Example |
|---|---|---|
| **Source value** | A value the source gave, copied or parsed, not changed in meaning. | `game.start_time_utc` from the schedule's `gameDate`; `season_summary.era` from the MLB API |
| **Documented derivation** | Computed by code from source values, by a rule written in `DECISIONS.md` or in this repository's code and named in the manifest. | `pitching_profile.swing_miss_label` (D24, D25); `putaway_pitch` (D30); `offense_profile.ops_vs_hand` from Savant plate appearances |
| **Label constant** | A constant that asserts nothing about data: a name, a title, a unit. | `metadata.project_name`; the section title "Arsenal Scout" |
| **Unavailable state** | The field says there is no value. | `bio: null`; `charts.strength_profile: []` |

Anything else is a violation, in particular a constant that asserts a fact (a status, a scope, a date, a record, a claim about data).

## 2. The eight rules

### Rule 1. Provenance

*Every published field is a source value, a documented derivation, or an explicit unavailable state. Constants only for labels that assert nothing about data.*

Examples from Annex A:

- `status: "upcoming"` for every live game was a constant asserting a fact (F5, closed in P0.15-D2.5a: it is the schedule's state through one table, `schema.GAME_STATUS`).
- `data_confidence.lineup_status: "probable_pitchers"` and `pitch_data_status: "fetched_snapshot"` were constants that asserted what the data contains (F5; `lineup_status` now follows the status, P0.15-D2.5a). `pitch_data_status` was one too (F1) until P0.15-D2.1b: it is now computed, `fetched_snapshot` when at least one starter has pitch data and `unavailable` (the word `sample.rates.source` uses) when none has.
- `charts.pitch_movement.*.*.family: "Fastball"` for an unmapped pitch is an invented derivation (F6e). Closed in P0.15-D2.2e: the family is `null`, the raw code stays as the source value, a warning is recorded, and a role (primary, put-away) held by an unmapped pitch is `Not available` (`labels.profile_pitches`): it never passes to the next pitch.
- `family` for a mapped pitch, `teams.*.record: null`, `bio: null` are correct: the first is a derivation from a name map, the others are explicit unavailable states.
- `critic_review.revision_notes` ended with "Avoided claiming official Stuff+." and "Kept the report focused on matchup fit rather than outcome prediction.", constants that asserted a check happened; no check stood behind the first (F8, closed in P0.15-D2.1c). The one note left, "No betting or outcome-prediction language found.", is written only when the betting-language check ran and found nothing.

**Schema 0.6.0 (D38, P0.15-D2.3).** `teams.*.offense_profile.vs_pitcher_hand` is `null` when the starter the lineup faces throws with a hand that is not `L` or `R` (`S`), and `starters.*.throws` may be `S`; the manifest asks the label to be the opposing hand when it is `L` or `R`, and unavailable, with no figure in the lineup, when it is not (`vs_hand_label`). The shape of `data_status.live_run.errors`, `warnings` and `reason` changes in the same version (P0.15-D2.3c).

**Series context (0.9.0, D43, P1.5).** `matchups[].series` is `null` for a game that is not a postseason game and, once the producer exists (row 7), an object `{series_name, game_number, games_in_series, standing}` for one that is; `standing` is `null` when the standing before first pitch is unavailable, and `games_in_series` when the schedule does not say. The producer (P1.5-b) takes the name, the number and the length from the day's schedule and the standing from the `seriesStatus.result` of the last played game before this one (two requests, none for game 1); a text is published only if `series.series_name` / `series.standing` recognize it (strict patterns fixed from one real answer of 2026-10-22, `tests/fixtures/mlb_series_2026-10.json`), else the part is `null` (a name the code does not know makes the whole `series` `null`: the page says nothing about a series). The manifest lists the four parts with a check each, so an unknown name, a number outside the series, a length a series does not have, a standing that cannot be true, an extra or a missing key is a finding. The same version lets a file have no matchup and no featured id (a day with no games) and lets an archive row have no result or grade; the page reads all three; the producer of the object is row 7, and the producers and the checks that accept an empty day and an archive row with no result, with the amendment of rule 6 (live archive) and F4, are row 9.

**Nullable by schema (0.5.0, D37, P0.15-D2.2c).** Three fields may be `null` because the world has no value for them: `charts.pitch_movement.*.*.family` for a pitch the family map does not know (F6e), `teams.*.abbreviation` and `starters.*.team` for a team the schedule and the maps do not know (F7), and `charts.pitch_mix[].<slot>.overall` for a starter who threw no pitch (F20). Every reader treats a `null` as unknown: a null share is a pitch not thrown, a team without abbreviation is shown by its name (`labels.team_label`, `lib/teamLabel.ts`), a pitch without family has no description and none is inferred from its name. Commit D2.2c makes the readers ready; the producers write the nulls in D2.2d (share) and D2.2e (family, abbreviation).

**Check (`data_pipeline/provenance.py`, section 6):** a manifest lists every path of a live file with its kind and, for a source value, its source. A leaf outside the manifest (`rule1:unlisted`), a constant that asserts a fact (`rule1:constant_asserts_fact`), a wrong type, a placeholder given as a value (`rule1:placeholder`), a family invented for a pitch the map does not know (`rule1:invented_derivation`) and a derivation that does not recompute (`rule1:derivation_mismatch`) fail validation. So do figures that cannot be true together (`rule1:impossible_figures`, section 6.5): a starter with more home runs than batters faced, more strikeouts, walks and home runs than batters faced, or more batters faced than pitches (F21, P0.15-D2.2f).

**Pitch-mix conservation (QA5-01, P0.16-d).** Each starter's complete source mix is retained internally. The ordered union of the two starters' top five (ranked by raw count, then name) selects the displayed rows only. Each displayed cell keeps that starter's count, total and per-side shares from the full source mix; a measured zero means the pitch is absent from that full mix, never merely below fifth place. Raw codes that share a published name are counted together. Velocity, movement and locations for a selected pitch likewise use the complete eligible source, with their existing availability thresholds. Only selected pitch names are projected to the public charts and location lists. Displayed counts need not sum to the starter's total because pitches omitted by both selections remain hidden. `tests/test_pitch_mix_conservation.py` compares every published count/share to independent source-row counts over the matrix and hard cases, including asymmetric six-type mixes, reversed starters, shared-name aliases and absent/hidden-pitch controls. Internal payload consistency alone cannot detect a plausible count that disagrees with the source.

### Rule 2. Unknown is never zero

*`null` when unknown. `0` only when the source measured zero. A column that cannot be used is unavailable plus a recorded error.*

Examples:

- `events` null in every row of a Statcast frame published `batters_faced 0`, `strikeouts 0`, `walks 0`, `home_runs 0` from source `statcast`, and the card showed K "0" (F6b). The code could not tell "no plate appearance completed" from "unusable column". The column is unusable: the counts are `null`, `sample.rates.source` is `"unavailable"`, and an error is recorded. (F6b, closed in P0.15-D2.2a; the fix is in `_statcast_counts`: the counts are `None` when no row ends a plate appearance).
- The analyst writes "no batters faced on record" and "no pitches on record" when the count is `null`, because it tested `if batters` (F14, closed in P0.15-D2.2b). A missing count is not a zero count: an unknown has its own sentence ("batters faced not available", "pitch count not available"), and so does the critic's evidence for a limited arsenal; the detail panel says "Pitch data is not available for X" instead of "has no pitches on record" when the pitch count is `null`.
- `_usage_pct` returning `None` for a side the starter never faced (P0.14-C) is correct; a real `0%` against a side he did face stays `0%`.
- `pitch_type` null in every row of a populated frame produced a debut with `pitches 0` and no error (F6a, closed in P0.15-D2.2a): the answer is rejected whole, as is a frame with no `stand` of `L` or `R` in any row, whose per-side shares would be `null` and which the page reads as "No left-handed batters faced.", a claim the data does not support.

**Malformed or incomplete (the criterion, owner 2026-10-15).** A source answer is one of three things, and each has one treatment:

| The answer | Example | Treatment |
|---|---|---|
| **Malformed**: a column the code needs is missing, or is present with no usable value where one is needed, or a row cannot say when or what it was | no `stand`, `pitch_type`, `release_speed`, `plate_x` or `plate_z` column (F6c); `pitch_type` or `stand` with no usable value in any row (F6a); a row with no valid `game_date` or `game_type` (QA4-02) | Rejected whole: a recorded `statcast_pitcher` error that names the column, and the game is not built from that answer. |
| **Unusable in one part**: the rest of the answer is sound but one figure cannot be read from it | `events` missing, or with no plate appearance in any row (F6b) | That figure is unavailable (`null`, `sample.rates.source = "unavailable"`) and an error is recorded; the game is kept. |
| **Well formed but incomplete**: it parses, and it says less than the world did | Statcast has fewer plate appearances than the API line (F21, closed in P0.15-D2.2f; section 6.5) | Degraded: the part that cannot be trusted is unavailable, an error is recorded, and the rest is kept. For F21: a recorded `statcast_pitcher` error, the starter's pitch data (mix, velocity, movement, locations, primary and put-away pitch) is unavailable and his pitch count is `null` (not `0`: he threw some), his hand stays, and the API counts are kept. |

A well-formed answer that is merely thin (a debut, a short season, a partial null in `pitch_type`) is a sample, not an error. `release_speed`, `plate_x`, `plate_z`, `pfx_x` and `pfx_z` with no value in any row are *columns that exist*, so they are not rejected: they leave velocity, locations and movement unavailable (`null` or an empty list, never `0`), which `tests/test_statcast_frame_usable.py` pins.

**Finite measurements within bounds (QA5-03, P0.16-b; QA6-01, P0.17-b).** Before filtering or aggregation, every populated, non-null value in a numeric Statcast column the pipeline reads must be finite and within the physical limits of one table (`PITCH_VALUE_BOUNDS` in `live_pipeline.py`): 30 < `release_speed` <= 110 mph; |`pfx_x`|, |`pfx_z`| <= 3 ft; |`plate_x`| <= 5 ft; -3 <= `plate_z` <= 10 ft. The limits are what a sensor can report, not thresholds of any label or claim; a value outside them is a malformed cell, not a rare pitch (a finite 9999 was published as a 119,988 in. break). Means and medians are also computed inf-safe: an aggregate that is not finite is unavailable, never `inf`. The five columns form three groups: velocity (`release_speed`), movement (`pfx_x`, `pfx_z`) and locations (`plate_x`, `plate_z`). A malformed numeric cell records `statcast_pitcher` / `malformed_rows` and makes its whole measurement group unavailable; valid counts, mix, hand, API line and other measurement groups stay. No partial mean/median is computed by silently discarding the bad row. Missing measurements (`None`/source `NaN`) keep the unavailable behavior above. Team batting derives its figures from categorical events and row counts; its cached numeric identifiers are unused. Independently, `validate_payload` rejects every non-finite number anywhere in any payload (including `NaN`), and JSON serialization uses `allow_nan=False`, leaving the previous file untouched on failure. `tests/test_domain_bounds.py` covers one case per column and side of each bound, the bounds themselves as controls, a two-game file where one bad cell leaves the other game whole, and the aggregation with the table widened on purpose. `tests/test_nonfinite_numbers.py` covers probe B, all five columns, sparse/negative infinity, retained games and public error codes, nested payload mutations, strict serialization, and finite/null controls.

**MLB API counts and placeholders (QA6-01, P0.17-b).** Every count the pipeline reads from the MLB API (`strikeOuts`, `baseOnBalls`, `homeRuns`, `battersFaced`, `plateAppearances`, series `wins` and `losses`) is an integer of 0 or more in `mlb_schemas` (kind `count`), and a series game number is an integer of 1 or more (kind `positive`); a negative or non-integer count fails the whole answer as a recorded source failure of that source (the pitcher's API line is then unavailable and Statcast counts stay the fallback), never a published number. ERA, WHIP, innings pitched, OPS and average are text in the API: a number is kept as written, and a placeholder (`-.--`, `.---`, `-`, an empty or any other non-numeric string, which is what a pitcher with no innings returns) is that one figure unavailable (`"N/A"` for ERA, WHIP and innings; `null` for OPS and average), with no error and no effect on the rest of the line or on the file. `tests/test_source_schemas.py` (counts, generated from the schemas) and `tests/test_domain_bounds.py` (placeholders, the debut shape, two games) cover it.

**Event outcomes and cached months (QA5-02/05, P0.16-c/c2).** One explicit mapping (`fetchers/statcast_events.py`) classifies known completed events and their scoring contribution for both pitcher counts and team splits. Its domain is checked against the unchanged MLB eventTypes response saved on 2026-10-17 (`tests/fixtures/mlb_event_types_2026-10-17.json`; one owner-authorized request). All 47 metadata codes with `plateAppearance=false` are non-PA, including caught stealing, pickoffs and runner outs; all 27 PA codes have explicit scoring classes, including triple plays and compound strikeouts. Tests fail on any missing code, wrong PA/hit flag or unclassified PA; no unknown code defaults to an out. The previously supported Savant-only `truncated_pa` is the sole extension. Metadata PA/non-hit values without another scoring exclusion use the non-hit at-bat class, not a claim of an out (including `fan_interference` and `os_ruling_pending_primary`). An unknown populated event is `unknown_value`, even among known outcomes or in a row later excluded by the cutoff. It cannot enter a denominator or default to an out. Statcast counts/rates become unavailable; valid independent API figures retain their existing precedence, and sound pitch data stays. When events cannot establish a count, the incomplete-sample comparison is skipped rather than dropping the starter. A populated team frame whose events are all null is recorded as `unusable_column`, with no offense figures or scope. Null intermediate pitch rows, known non-PA events, valid empty answers and measured zero rates from known outcomes remain valid. Errors and fielder's choices are known at-bat outcomes, not evidence of a literal out.

The team-month boundary checks all required columns (including `events`), row/event validity and the row cap before caching, and applies the same checks to cache hits. A malformed cached month is a miss: refetching uses the existing closed/open request caps and pacing. Only a valid replacement overwrites it; an invalid fresh answer never becomes a cached month. Blank fresh responses are normalized to a valid empty frame; header-only CSVs must have the full required column set. `tests/test_statcast_event_domain.py` and `tests/test_statcast_cache_integrity.py` cover probes C/D, unknown/unusable outcomes, no-API labels, known scoring classes, poisoned-month repair, failed replacements, budgets and legitimate empty/non-PA controls.
- A starter who threw no pitch has `charts.pitch_mix[].<slot>.overall = 0` for each pitch his opponent threw (F20): a share of zero pitches is unknown, `null`, not 0%. His `count` of 0 out of a `total` of 0 is the measured zero; the share is what cannot be computed. Closed in P0.15-D2.2d: `_combine_pitch_mix` writes `null` out of a `total` of 0 and `0` only out of a positive `total`; the publication check accepts only `null` out of nothing; the readers (the critic, `report_facts`, the registry, the detail panel, the chart) were made null-safe in D2.2c.

**Check (`data_pipeline/provenance.py`, section 6):** the manifest names, for every numeric field, the evidence a `0` requires (section 6.3). A `0` without its evidence fails (`rule2:zero_without_evidence`); so does an unknown value written as a number for a source that is `unavailable`, or as `"0"`, `""` or `"N/A"` text in a numeric field (`rule2:unknown_written_as_value`). A guessed default such as a throwing hand is found by the matrix, not by the payload: the hand is a source value and the payload cannot say which source gave it (`tests/test_matrix.py` makes the people endpoint answer the opposite of the guess).

### Rule 3. Scope

*Each group of figures carries the scope of its source. No scope is stated for a group without figures.*

A group has a figure when a value is known, **a measured zero included** (rule 2): a debut's 0 pitches come from a valid Statcast answer, so `sample.arsenal.scope` stays and says which games the zero was measured over. An unknown value (`null`, `"N/A"`, a `sample.rates.source` of `"unavailable"`) is not a figure: the group has no scope in any field that carries one, and the field is `null`. A scope is a field; the sentence that states it (rule 4) follows the same rule.

The constructors decide this, not the checks: `labels.build_sample` writes `sample.arsenal.scope = null` when the pitch count is unknown and `sample.rates.scope = null` when the counts are unavailable; `live_matchup.build_offense` writes `offense_profile.scope`, `summary_label` and `recent_form` only when the lineup has an OPS, K% or BB% (a split with none of them is no split). These fields are nullable since schema 0.4.0 (P0.15-D2.1a), and a live snapshot is read only if its `schema_version` is exactly the code's (`schema.snapshot_matches_schema`; a missing or different one is rejected). The file says only `data_status.reason = {source: "snapshot", code: "snapshot_schema_mismatch"}` (rule 8); the versions go to the local log. Recorded as D36.

Groups at HEAD: pitch data (Statcast; `sample.arsenal.scope`, `charts.*`), season rates (ERA, WHIP, innings; MLB API; `scopes.season_rates`), counts (strikeouts, walks, home runs, batters faced; the API or Statcast; `scopes.counts`, `sample.rates.scope`), team offense (Savant; `offense_profile.scope`). Scope is `regular_season` or `regular_and_postseason`, through the cutoff (D29).

**Source of the counts** (QA3-02, P0.14-A). The four counts (batters faced, strikeouts, walks, home runs) come from the MLB API line when it gives all four. Otherwise they come from the valid Statcast plate appearances, if the starter has pitches. Otherwise they come from a partial API line, if it has any count. Otherwise they are unavailable (`sample.rates.source` is `"unavailable"`, every count `null`). Sources are never mixed field by field. `sample.rates.source` says which one gave them, and the scope of the group is that of the source: regular season for the API, the scope of the pitch data for Statcast.

Examples:

- ERA from the regular-season API labelled "regular season and postseason" because the counts came from Statcast (QA4-01, closed in P0.15-B).
- `offense_profile.scope` was set while every offense figure was `null`, and the analyst wrote "Team offense splits cover the regular season through D" one sentence after "Season offense splits were not available" (F2, closed in P0.15-D2.1a).
- A starter with no figure in any group has no scope (closed in P0.15-B: "no season figures are available").
- `sample.rates.scope` was set while the counts were unavailable (`sample.rates.source` is `"unavailable"`), though `season_summary.scopes.counts` was `null` (F17, closed in P0.15-D2.1a). `sample.arsenal.scope` with `pitches == 0` is **not** this: the zero was measured.

**Check (`data_pipeline/contract_checks.py`, `GROUPS`):** one table of groups (pitch data, season rates, counts, offense), each with how to tell that it has a figure, every field that carries its scope, and the source rule. A figure without a scope, a scope without a figure, or a scope that disagrees with the source of its group fails (`rule3:<group>#figures_without_scope`, `#scope_without_figures`, `#scope_disagrees_with_source`). Only live matchups are asked. No sentence says "all figures" about a starter whose groups differ.

### Rule 4. Claims

*Every sentence that asserts a fact (agent text, UI text or workflow text) declares the fields that make it true and is emitted only when they do. This applies to JSON nobody renders.*

- Each emitted phrase is recorded as a claim `{id, key, args, subject, location}`. The sentences of a matchup (report, critic review, data confidence notes, postgame) are in `matchups[i].report.claims[]`, with locations relative to the matchup (`report.sections[1].body`); the sentences the generator writes (workflow, data label) are in `claims[]` at the root, with locations from the root. `subject` is the starter the sentence is about (`away_starter`, `home_starter`) or `null`; `location` is `null` for a part of another sentence. `metadata.language` says which catalog the keys belong to.
- `args` are values copied from the payload (a name, a number, a label, a scope) or `{"claim": id}`, a reference to a claim that is part of the sentence (a plural such as "3 home runs" inside a longer sentence). Never an internal (a path, an exception, a function name, an object). Two pseudo keys build sentences out of sentences: `@join` (args `sep` and `parts`) and `@capitalize` (arg `of`); they assert nothing themselves.
- The text of a report is exactly the join of its registered phrases. The validator renders each claim again from its key and args and requires the text of the field to be exactly that; a text field with no claim, a claim for a field that does not exist, a part that no sentence uses, or a sentence edited after the fact fails. Which fields are text is a list in `data_pipeline/claims.py` (`MATCHUP_TEXT_PATHS`, `ROOT_TEXT_PATHS`); the static content of the demo (archive rows, bios) is not agent or generator text. The sources and disclaimers became mode-dependent in P0.15-D2.4b; they are labels of a closed set per mode judged by the manifest (section 6.1), not sentences of the generator, and stay out of the list.
- Each key has a condition in the registry (section 3). The validator evaluates it on the payload and the args. A phrase whose condition is false fails (`rule4:<key>#<reason>`).
- **A text argument is a payload value, a reference, or one of the forms below.** `tests/test_claim_args.py` fails over the four generated payloads, the fourteen golden scenarios and the served file if a text argument of any claim is none of these: a reference `{"claim": id}`; the separator of an `@join`; the empty text (a qualifier that is not written); or a value of the payload outside the sentences, written in one of these forms. The list is closed: a new form needs its reason written here and a test.
  1. *As is*: a name, a label, a scope or a pitch exactly as the payload has it. The sentence quotes the value.
  2. *Lower case*: `solid command`, `four-seam fastball`. A label or a pitch in the middle of a sentence is written in lower case; the value does not change.
  3. *First letter in lower case*: `above-average swing-and-miss ability`. A rate label ("Above-average swing-and-miss ability") that follows its subject ("He shows …") loses its capital and nothing else. The same form quotes a series standing that starts with "Series " (`Series tied 1-1` is written `series tied 1-1` after "Before first pitch,"); a team standing ("BOS leads 2-0") is quoted as it is (`series.in_sentence`).
  4. *Without ` fastball`, then lower case*: `four-seam`, `sinker`. The data says "Four-seam Fastball"; a sentence says the pitch by its short name.
  5. *A number written as text*: the number of the payload as Python writes it (`str(n)`) or without a trailing zero (`12.0` is `12`). The critic writes a share inside a sentence. A figure computed from two payload numbers (a percentage of two counts) or grouped with thousands separators is not a form of a payload value; the condition of its key in the registry checks it against the raw counts (`critic.pitch.low_counts`).
  A piece cut out of another sentence (the action of a question, the names of two starters joined with `", "`) is none of these: it is its own phrase, referenced (`analyst.watch.action.*`, `@join`).
- **The condition of a claim about data is evaluated on the payload, never by running the critic again.** A claim about data (`critic.pitch.*`, `critic.names.*`, `critic.limited.*`, `critic.command.*`, `critic.scope.*`, `critic.betting.*`) is checked against the fields it speaks about: `count`/`total` of the pitch mix, `sample`, `scopes`, the labels, and the text of the report read with the words of the catalog (`data_pipeline/report_facts.py`). Running the critic again is only for claims about the process (`critic_review.summary` and the notes), and those read the published `checks`, not the critic: the critic is the only definition of what a check is. `tests/test_registry_no_critic.py` fails if a module that checks the contract imports the critic, or if the contract cannot run over the corpus with every function of the critic made to fail. `tests/test_critic_facts_differential.py` measures what that independence costs: it runs the critic and `report_facts` over every report of the corpus and the matrix, and over reports with injected sentences, and fails if they disagree on who a sentence is about, which pitches it names, or the verdict of the names, limited-arsenal, command, scope or betting check. Its injection layer assumes that how a pitch is named does not depend on the matchup, so its variants rotate over 13 matchups chosen for coverage (every combination of limited arsenal, differing groups and command label of a starter, and every relation of the two pitch sets) instead of crossing with all of them; a test checks that the injected sentences reach every branch of the critic's data checks in those matchups. A sentence that reports a problem the data has (`critic.names.credited`, `.nobody`, `.unsupported`, `critic.limited.unsupported`, `critic.command.wrong_*`, `critic.scope.unsupported`, `.all_claimed`, `critic.betting.unsupported`) is never in a published file: the generator stops on an `unsupported` check (rule 5, exception), so the check reports it (`#published`).
- No agent phrase names a pitch that is not in the mapped set (see rule 8, warnings).
- A text that says a game is upcoming ("upcoming", "tonight", "before first pitch", "today") is emitted only when the source state is `Preview` (and for "today", the game's date is today in its official zone). It never appears for a game whose state is `Live` or `Final`. The same holds for a statement that is only true before the game: "the series has not started" (`analyst.series.opening`) is written for a game whose state is `Preview` and for no other, an unknown state included (QA1-01).
  - **One exception, stated by name: `analyst.series.standing`.** "Before first pitch, {result}." is framed as the standing before first pitch in its own words, and the standing is computed as of the day before the game (D29: `game_date - 1`), so it is a statement about the past that stays true in every state, an unknown one included. It is the only phrase that says "before first pitch" outside a `Preview` game, its registry condition asks for no state on purpose, and `tests/test_series_state.py` runs it over the four states.

Examples:

- "This report uses a fetched live snapshot with probable pitchers and Statcast pitch data" was written for a game of two debuts, with no pitch data (F1, closed in P0.15-D2.1b: the note is now built from parts, one per starter and per lineup). The condition of the Statcast part is that a starter has `sample.arsenal.pitches > 0`; the condition of "season offense splits" is that both teams have a split.
- "Lineups can still change before first pitch" for a game already in progress (F5, F16).
- "Today's Matchup Summary" asserted a date that the file cannot guarantee (F16, closed in P0.15-D2.5c: the title is the neutral "Matchup Summary" in every mode).
- "No betting or outcome-prediction language found." is supported by the betting-language check; the check's result is its condition (F8, closed in P0.15-D2.1c).

### Rule 5. Isolated failure

*An error is contained in the smallest unit: a field, a dimension, a game. One bad game never takes down the page.*

- A bad field is its unavailable state plus a recorded error (rule 2). A bad dimension is flagged `limited` (D1, D24). A bad game is dropped from the file with a recorded reason and the other games are published.
- One unsafe game does not reject the snapshot (F11, closed in P0.15-D2.3b). The checks of the run and the snapshot (schema, run identity, the run's cutoff and game day) are whole; the checks of a game drop that game, with a recorded `{source: "snapshot", code: "game_rejected"}`, and the other games are published; the page falls back to the demo only when no game is left. A starter whose hand is `S` is published (`fetch_pitcher_hand` accepts it and so do the generator and the publication check): a lineup has a split only against `L` or `R`, so the lineup he faces has `vs_pitcher_hand: null`, no figure, no summary label and no scope, and the analyst writes "Season offense data cannot be matched to this pitcher's hand, so the lineup read makes no offense claims." (F15, D2.3a). Before, `build_offense` read the right-handed split for him under the label "SHP".

**Explicit exception (integrity gate, fails closed).** `critic_review` with an `unsupported` check, and `validate_payload`, still stop the whole file: the generator exits 1, nothing is written and the previous file stays (P0.12-B). The reason is that a claim the data does not back up must not be published; stopping is the safe direction. This is not an isolated failure and is recorded as an exception. Whether to drop only the affected game is reviewed in P1.2.

### Rule 6. Honest mode

*The page states whether it shows live or demo data. A live file contains only live content.*

- `metadata.data_mode` is `fetched_snapshot` (live, including a valid no-games day), `demo_fallback` (a live run failed) or `demo_cached` (no run). The page shows a visible line: "Live data · fetched {date}" or "Demo data: live data unavailable" (and a demo-labelled text for `demo_cached`).
- In a live file every matchup is a live matchup (`data_confidence.level == "fetched_snapshot"`). D43 supersedes the empty-only archive rule of P0.15-D2.4a: P1-R2-b carries the previous file's archive and earlier matchups only when that file is live. A demo/fallback file supplies no rows. The previous-file boundary checks every consumed field and rejects malformed live input; it does not rejudge historical report text against the current catalog. Rows are unique by date and report id (`{date}:{matchup_id}`), earlier than the current target, newest first, at most 60. Result and grade stay null (no automated postgame, D41); status is the earlier schedule state, with null preserved when unknown (D40). The public row has no origin field: the boundary/construction establishes lineage, while the manifest and rule 6 validate the row's shape, date, ordering, uniqueness and ungraded state. Those file-only checks cannot independently reconstruct historical lineage. The first live day has no archive; "No past reports yet" is emitted for an empty archive. Today's report never becomes a past report.
- A valid no-games file has `live_run.status == no_games`, integer-zero scheduled/live counts, empty errors/warnings, a canonical target date, cutoff one day earlier, an instant for `run_at`, null reason and featured id, and `matchups == []`; fetch time equals that run's instant. A malformed/failed run cannot claim this state. `daily.py` writes it atomically and exits 3; `--check` accepts it with exit 0. The workflow accepts build exit 3 as success. The page shows "No MLB games scheduled on {date}." above the archive. The workflow counts zero matchups and retains only its pending scout step, "Loaded data for 0 matchups."; report/critic/postgame steps and their claims are omitted because no report or featured game exists.
- Texts that describe the data source ("Cached demo", "cached matchup data", "Cached demo data may be used…") appear only in a demo file. In a live file the equivalent text is neutral (F3, closed in P0.15-D2.4b): `metadata.data_sources` lists the two live sources (the sources the live run consults, not a promise that every field of every game came from both) and `disclaimers` has the four live ones (`config.LIVE_SOURCE_LABELS`, `config.LIVE_DISCLAIMERS`: the attribution to MLB and Baseball Savant, "PitchCraft is free and non-commercial: no ads, no sponsorships and no paid features.", "Requests to the data sources are cached and the data is not downloaded in bulk." and the information-only note, P1.9, D16; the manifest accepts only those in a live file), the first step of the workflow says "Loaded data for N matchups." in every mode, and the hero and the layout describe the product, not the data. A demo file keeps its demo sources and disclaimers. The mode line is `ModeLine` (inside `Hero`); `formatModeLine` says "live" only for `fetched_snapshot` and shows the demo line for any other mode, known or not.
- `metadata.data_fetched_at` is the time of the live fetch (the run's `run_at`), `null` in a demo file. `metadata.generated_at` is the time the file was built, always real, in every mode: the generator's clock (`build_payload(now=...)`, injected by tests; a clock without a zone is refused). They are never the same field (F9, closed in P0.15-D2.4c; schema 0.7.0, D39). Every label that says "fetched" shows the day of `data_fetched_at` in America/New_York (`schema.new_york_day`), never the game day and never the UTC date. A live file needs `data_fetched_at` to be an instant with a zone (`rule6:data_fetched_at`; the manifest types it, `rule1:wrong_type`), a run whose time is not one is not published as live (`snapshot` / `snapshot_mismatch`), and `validate_payload` refuses a demo file that has one ("a demo file has no time of fetch").

Examples: F3 (the Hero says "Cached Demo" over live data), F4 (`matchup_002`, "BOS 5 - NYY 3" and a postgame grade next to a live game), F9.

### Rule 7. Real state and time

*Game status comes from the source. "Today" is computed in the game's official zone.*

- The published `status` is derived from the schedule's game state through one table, `schema.GAME_STATUS` (F5, closed in P0.15-D2.5a; schema 0.8.0, D40): `upcoming` (`Preview` / `Scheduled` or `Pre-Game`), `live` (`Live` / `In Progress`), `final` (`Final` / `Final`, `Game Over` or `Completed Early`), and `null` for every other pair, a missing part included. `abstractGameState` alone is not enough: measured on 2026-10-16 over 208 games, a postponed or cancelled game arrives as `Final` with `detailedState` `Postponed` or `Cancelled`, so `final` means a game that ended. The table lists only the pairs the owner named or a real answer showed; it grows with real answers, not by guess. `data_confidence.lineup_status` follows the status (`probable_pitchers` for upcoming, `game_started` for live and final, `null` for `null`). A live game that is `final` keeps its pregame report and its postgame stays `null` until the daily postgame exists (P1.2): it is never sent to the grader.
- A live or final game keeps the pregame report (the cutoff is the day before, D29) and shows its real status. The postgame stays `null` until the daily postgame exists (P1.2); no text promises one.
- The official date of a game is `officialDate` (America/New_York, D29). "Today" on the page is the current date in that zone, not the UTC date of the machine that renders it (F12, closed in P0.15-D2.5b: `lib/format.ts` `todayInNewYork`, the same `newYorkDay` that the mode line uses).
- A start time is a UTC instant shown in the venue's zone when the schedule gives one, otherwise as UTC (D33).

### Rule 8. No internals in the public file

*Errors are published as `{source, code}`, never raw messages.*

- `data_status.live_run.errors` and `data_status.reason` carry exactly a `source` from the fixed set `contract_checks.RUN_SOURCES` (`mlb_schedule`, `mlb_person`, `mlb_season_stats`, `mlb_team_splits`, `mlb_series_status`, `statcast_pitcher`, `savant_team_batting`, `snapshot`, `pipeline`) and a `code` from the closed set `RUN_ERROR_CODES` (`request_failed`, `malformed_response`, `malformed_rows`, `missing_column`, `unusable_column`, `budget_spent`, `unknown_value`, `incomplete_sample`, `unexpected_error`, `no_games`, `no_usable_games`, `game_rejected`, `snapshot_mismatch`, `snapshot_schema_mismatch`, `no_live_run`). Both sets are D38 (schema 0.6.0); `no_live_run` was added to the codes in P0.15-D2.4b and is recorded in D39 (the reason of a demo file, not an error of a run). Exception messages, paths, pitcher ids and file names stay in the local run record (`data_cache/processed/live_run.json`), which is not published, and in the console log.
- What publishes them is `generate_demo_json._run_summary`: each error is exactly its `source` and `code`, the first of each kind only, at most 20; a record whose source or code is not in the sets is published as `unexpected_error` (its source kept if it is in the set, `pipeline` otherwise), never as its text. `live_pipeline._record_error(source, code, message, **context)` is the only way a failure is recorded, and `error_code(exc)` the only place that maps an exception to a code (a class of the module or of `mlb_schemas` says what it is; `OSError` is `request_failed`; anything else is `unexpected_error`).
- `data_status.reason` is `null` for a live file and `{source, code}` for a fallback: an unreadable run record or snapshot is `snapshot` / `malformed_response`; a failed run says the source and code of its first error; a valid no-games run is live (P1-R2-b), while a malformed no-games record is `snapshot` / `snapshot_mismatch`; games with none usable is `pipeline` / `no_usable_games`; the snapshot of another run (or one that fails a check of the run) is `snapshot` / `snapshot_mismatch`; a snapshot whose every game is rejected is `snapshot` / `game_rejected`; one of another schema is `snapshot` / `snapshot_schema_mismatch`. A demo file for a day with no live run at all says `pipeline` / `no_live_run` (P0.15-D2.4b): no free sentence is left in `reason`, in any mode. It is not a failure of a source, and rule 8 is asked of a live file only.
- A **warning** is recorded the same way, `{source, code}`, in a separate `warnings` list. It never changes the run status. The warnings at HEAD: `statcast_pitcher` / `unmapped_pitch_type`, when a pitch code is not in `PITCH_NAME_MAP` (the pitch keeps its raw code as the source value, `family` is `null`, and no agent phrase names it, F6e), and `savant_team_batting` / `unknown_team`, when a team id has no Statcast team code (its offense split is unavailable and its abbreviation is `null`, F7). The run record (`live_run.json`) carries them since P0.15-D2.2e and the file publishes them (`data_status.live_run.warnings`, same shape, at most 20) since P0.15-D2.3c; a warning whose source or code is not in `RUN_WARNING_CODES` is left out.
- F10 is closed (P0.15-D2.3c): the file no longer publishes `message`, a pitcher id or free text; `rule8:error_shape` and `rule8:reason` left `known_violations.py`.

## 3. Registry of claims

Every key that asserts a fact, with its condition on the payload. `m` = the matchup; `s` = the starter the phrase is about; `o` = his opponent's starter; `team` = the lineup the phrase is about (the opponent of `s`, so `team.offense_profile` is the offense `s` faces). Paths are relative to `m`. "Live" conditions are evaluated on live files; demo-only keys are emitted only in a demo file (rule 6). The machine form is `data_pipeline/claims_registry.py` (P0.15-D3.2); a test fails if the two differ, or if a catalog key is neither here nor in section 3.5.

## 5. How this is checked

1. **Tests first** for every fix (`docs/ENGINEERING.md`): reproduce the finding, see it fail, then fix.
2. **Generic checks** (P0.15-D3): `validate_payload` applies rules 1 to 4, 6 and 8 to every field and every recorded phrase of every file, not to the cases someone thought of. Selected real negative tests show rejection of particular false conditions. The registry reporting guard now named `test_each_reached_rule_reports_through_the_checking_mechanism` forces `Ctx.require` to report; it does not falsify payload conditions or establish full registry coverage. P0.16-f adds 25 genuine payload/claim negatives for the conditions affected by QA5. `STATUS.md` lists the 48 of 116 registered rule patterns without a documented semantic-negative assertion; even a tested pattern can have untested reasons, wildcard keys or branches.
3. **Matrix** (P0.15-D3): 72 combinations, API (complete, partial, absent) × season (regular only, with postseason) × starter (debut, limited, healthy) × day (normal, opening day) × throwing hand (present, missing), each through pipeline → generator → `validate_payload`; per case the game is published or fails with an explicit recorded error, and the contract holds. The cells are defined in `tests/matrix.py`: the away starter varies and the home starter is healthy; "hand missing" means the Statcast frame has no `p_throws` and the people endpoint answers `L` (the opposite of a guessed right hand); on opening day the cutoff is before the season, so every starter is a debut and the cells that no source can tell apart must publish the same file. The API line of each cell is a function of the starter's frame (`stat_line`); a starter with no pitch has no line, so "complete" and "partial" are the same empty answer for him, and the hard cases `statcast_gap`, `statcast_short`, `statcast_short_season`, `two_gaps` and `unknown_figures` drive F21. The hard cases outside the product (two debuts, two limited, the other side of the pair, real API zeros, no Savant data, `events` or `pitch_type` null, an unmapped pitch code, an unknown team, a failed hand lookup, a switch pitcher, a frame without a needed column, a starter without a hand) are in the same module. A finding the payload cannot show was an `xfail(strict=True)` labelled with its F until its fix in P0.15-D2; none is left since D2.3b.
4. **Frontend phrases** (3.3) are not in the JSON, so `validate_payload` cannot see them: component tests must check their conditions. P0.16-e checks its measured-movement and median/unavailable-location sentences with actual states and hand changes, including missing measurements/velocity, measured zeros and limited samples. This is separate from the Python registry and is not evidence of complete coverage of every frontend branch.
5. **No tolerance** (P0.15-D2.5c): there is no allowlist for a violation reported by the checks. The temporary table and the code of `validate_payload` that read it are deleted; `tests/test_no_tolerance.py` fails if the module, a table of violation codes, an import of it, an `xfail` or a skip for a finding of the contract comes back, or if a payload with one violation is published.
6. **QA gate** (D27): QA checks compliance with this contract as a finding area of its own.

## 6. The manifest of a live file (rules 1 and 2)

`data_pipeline/provenance.py` (P0.15-D3.3b-2). `MANIFEST` is a table of entries `(pattern, kind, origin, types, nullable, check)`. Every leaf of a live file, and every empty list or map (the unavailable state of what it would hold), must match one entry. Demo matchups inside a live file are not walked: they are rule 6's finding (F4). Every historical archive row is walked under D43 (P1-R2-b). A demo file is not asked.

### 6.1 Kinds

| Kind | Meaning | The check |
|---|---|---|
| `source` | A value the source gave. | The type, the format (a date, a UTC instant, a team abbreviation) and the evidence a zero needs. |
| `derivation` | Computed by a documented rule. | The value is recomputed from its inputs and compared: the pitching profile from the pitch mix and the sample (D24, D25, D30), `limited` from the sample, the family from the pitch map, the lineup's hand from the opposing starter, the title of a game from the teams. |
| `label` | A constant that asserts nothing about data. | The type, and a closed set where there is one (the schema version, the names of the agents, the thresholds of D24). |
| `claim` | A sentence, or the record of the sentences. | Rule 4 owns the condition. |
| `fact` | A constant that asserts a fact, written fixed without looking at the outcome. | It is a violation by definition, with the finding it belongs to. The fix of that finding turns the entry into a derivation with its evidence. |

A `null` is allowed only where the entry says `nullable`. The codes are `rule1:unlisted`, `rule1:null_not_declared`, `rule1:wrong_type`, `rule1:constant_asserts_fact`, `rule1:derivation_mismatch`, `rule1:placeholder`, `rule1:invented_derivation`, `rule2:zero_without_evidence` and `rule2:unknown_written_as_value`, each followed by `#` and the pattern of the entry. A check that cannot read its neighbours (a malformed sample) fails closed with `rule1:derivation_mismatch`.

### 6.2 Statuses: derivation or constant that asserts a fact

The owner's criterion (2026-10-13): a status is a documented derivation if it is set from the real outcome of the step (the agent ran and finished); it is a constant that asserts a fact if it is written fixed without looking at the outcome. Applied to every status the manifest finds:

| Field | How the code sets it | Classification |

### 6.3 The evidence a zero needs

| Field | A `0` is evidenced by | Otherwise |
|---|---|---|
| `sample.arsenal.pitches` | The pitch mix has no pitch thrown by that starter | `zero_without_evidence` |
| `sample.arsenal.pitches` (`null`, F21) | Not a zero: the count is unknown because his Statcast answer was incomplete, so no pitch of his is in the mix | `derivation_mismatch` if the mix has a pitch he threw |
| `sample.rates.*` (source `mlb_api`) | The MLB line gave it | Accepted |
| `sample.rates.batters_faced` (source `statcast`) | The starter threw no pitch | `zero_without_evidence` (F6b, closed in P0.15-D2.2a: the pipeline no longer produces it; the check stays for any other writer) |
| `sample.rates.strikeouts`, `walks`, `home_runs` (source `statcast`) | At least one plate appearance was counted | `zero_without_evidence` (F6b) |
| `sample.rates.*` (source `unavailable`) | Not applicable: every count is `null` | `unknown_written_as_value` |
| `charts.pitch_mix[].<slot>.total` | The starter threw no pitch (a total above 0 equals his pitches) | `zero_without_evidence` |
| `charts.pitch_mix[].<slot>.count` | A `total` above 0 (a real zero out of his own total), or no pitch at all | `zero_without_evidence` |
| `charts.pitch_mix[].<slot>.overall`, `vs_lhh`, `vs_rhh` | A `total` above 0: the share is `count / total`; out of nothing it is `null`. A `null` `overall` out of a positive `total` is `derivation_mismatch` (a share exists), checked since D2.2c | `zero_without_evidence` (F20) |
| `charts.velocity_by_pitch[].*` | A velocity is never 0 | `zero_without_evidence` |

`season_summary.strikeouts`, `walks` and `home_runs_allowed` are the counts of `sample.rates` and are checked by equality. `era`, `whip` and `innings` are text by type: a number written as text, or the sentinel `"N/A"`.

### 6.4 The limit of the zero check

The payload does not carry the Statcast `events` column, so a zero count is judged by what must hold around it. A starter hurt on his first pitch has pitches and no batter faced; the pipeline cannot tell him from a frame whose `events` is unusable (F6b) either, so his counts are unavailable instead of `0` (the safe direction), and the check reports a Statcast zero next to pitches as a zero without evidence. That is the safe direction: a false alarm stops publication, and the case is extremely rare. A real zero that the MLB API measured is accepted, and so is a Statcast zero that sits next to counted plate appearances. Percent strings of a lineup (`k_rate_vs_hand: "0.0%"`) are not checked for evidence: the payload does not carry the plate appearances behind them.

### 6.5 Figures that cannot be true together, and an incomplete Statcast sample (F21)

Two checks, one mistake: a starter's figures that come from two different samples.

**The invariants (`provenance.impossible_figures`, code `rule1:impossible_figures#<which>`).** A home run is a batter faced (`home_runs_over_batters_faced`); a strikeout, a walk and a home run are different plate appearances (`outcomes_over_batters_faced`); every batter faced took a typed pitch (`batters_faced_over_pitches`). Each is compared only when both figures are known (`null` is unknown, never compared). Only a starter with a `sample` is asked; a demo starter has none. Tolerance: an intentional walk is a batter with no typed pitch (Statcast writes a row for it with no `pitch_type`), so `batters_faced <= pitches` could fail only for a sample smaller than one pitch per batter, a few batters. The check is added with its fix and is not in `known_violations.py`.

**The incomplete sample (`live_pipeline.incomplete_sample`).** The API line (`byDateRange`, regular season, opening day to the cutoff) and the plate appearances that end in a regular-season row of the Statcast frame (same window; the postseason is not counted) are two counts of the same thing. When the line gives `battersFaced` and the frame has usable `events`, fewer plate appearances in Statcast than batters faced in the API line is an incomplete sample, and an empty frame next to a line above 0 is its extreme case (not a debut, a gap). The correction is the one of rule 2, "Malformed or incomplete". Not covered, on purpose: Statcast with *more* plate appearances than the API (the API is the official line), a partial line without `battersFaced` (nothing to compare), and a frame whose `events` is unusable (its own error is recorded, F6b).

**Tolerance, measured (P0.15-D2.2f, 2026-10-15).** The plan assumed one plate appearance per appearance (the API credits a batter to the pitcher who started the plate appearance, Statcast to the one who finished it). It was measured instead: `tests/fixtures/statcast_vs_api_pairs.json` holds 28 real pitchers (818 appearances, 9,414 batters faced, relievers included), each pair taken from the MLB Stats API (one request per pitcher, cached under `data_cache/raw/mlb_api_calibration`) and the cached Statcast frame, and the gap is **0 in all 28**, intentional walks included (`api_intentional_walks == statcast_intent_walks` in every pair). So `STATCAST_PA_TOLERANCE` is 0. A tolerance of one per appearance would have made the check vacuous for any pitcher with 25 or more appearances (a whole missing start of about 25 batters would pass). Two further real pitchers (traded in-season) hold a cached frame of their second club only (12 of 15 appearances, 11 of 66): those partial frames belong to the calibration cache, not to the pipeline. Measured on 2026-10-16 with one real request (D16), the live path for 605242 brings all 15 appearances and 61 plate appearances, the 61 batters faced of his aggregate line. Against that line (the aggregate split: 61 and 246 batters faced) the rule calls both cached frames incomplete. Since P0.15-D2.3d (F22) `fetch_pitcher_season_stats` reads that aggregate (it read `splits[0]`, the first club: 15 and 203 batters faced, so F21 caught 670167 and missed 605242), and the tests of the two frames run through that path (`tests/test_traded_pitcher_line.py`). The window of the calibration is, by construction, the pitcher's last regular-season game in the frame, so a frame that lags a night behind the API (a run right after late games) was not sampled; the direction is safe (pitch data is dropped, the API counts stay). A caller that passes a `season_start` later than January 1 would compare a shorter Statcast window with the API's whole season and flag good frames; the production callers do not pass it. If a future run shows a real gap, the constant and this paragraph change together, with the new pairs added to the fixture.
