## Amendment to commit d (2026-10-16, found while implementing; reported to the owner)

The plan's rule for the aggregate was "the split with no `team`". The real answers cached for the calibration show it is wrong for pitchers with one club: all 28 of them come back as that club's split twice, the second one with `sport` `{"id": 0, "code": "All"}` and the team still there; only the two traded pitchers have an aggregate with no team (and `numTeams` 2). With the plan's rule every pitcher with one club would have been a malformed answer. The rule implemented is: no splits, `{}`; one split, it; several, the one with `sport.id` 0, which must not have fewer batters faced than any club split; none, two, or a smaller one, a malformed answer (recorded `malformed_response`, `{}`), never the first and never a sum. `mlb_schemas.PITCHER_STATS` learns the optional `sport.id` (not `team` or `numTeams`). Open, not decided here: if a pitcher also played in the minors that season and the API lists those splits, the roll-up may include them (none of the 30 cached answers has a non-MLB sport); the calibration cannot see it.
