## 3. P1.0 — workflow security, and what covers `gh` and the REST API

**3.1 Workflow baseline (row 1).** Files: `.github/workflows/tests.yml`, `statcast-probe.yml`, `requirements.txt`, `requirements-dev.txt`, a new `tests/test_workflows.py`.

- Every `uses:` pinned by a 40-character commit SHA, on versions that no longer run on Node 20 (`actions/checkout`, `actions/setup-python`, `actions/setup-node`, `actions/cache`, `actions/upload-artifact`, `actions/download-artifact`). The SHAs are looked up at implementation time from the release tags (read-only GitHub reads) and each is written with its version in a comment. The repository setting "Require actions to be pinned to a full-length commit SHA" is turned on by the owner (G5): GitHub then refuses an unpinned action even if someone adds one later.
- `permissions: contents: read` at the top of every workflow, widened per job only where a job needs it (nothing needs `contents: write`: publishing goes through the deploy key, section 4). `persist-credentials: false` on every checkout. `ubuntu-24.04` everywhere. No `pull_request_target`; no secret outside the one job of `daily.yml` that runs in the `data-publish` environment.
- A new CI job `site` runs `npx tsc --noEmit`, `npm run lint` and `npm run build` next to `npm test` (they run today only in the implementer's terminal).
- `requirements.txt` pins every Python package CI installs: pandas, numpy and the rest of the tree that `pybaseball==2.2.7` pulls in, taken from `pip freeze` of a clean install on the CI Python (3.14), plus `requests`. Dependabot is not added (it would open pull requests).
- `tests/test_workflows.py` reads every file in `.github/workflows/` and fails on: an action not pinned to a SHA, a missing top-level `permissions`, a `runs-on` other than `ubuntu-24.04`, `pull_request_target`, a `secrets.` reference outside the publish job, a `contents: write`, an `echo`/`print` of a `secrets.` value, a push trigger with no `branches` filter, and a checkout without `persist-credentials: false`. Controls: `statcast-probe.yml` and the `components` job pass today; the `pytest` job of `tests.yml` checks out without `persist-credentials: false`, so that file is fixed in the same commit; one negative test per rule feeds the guard a broken workflow text.
- Acceptance: the CI of the commit runs the new job green, the guard test is red on each broken sample, and `statcast-probe.yml` still passes the same rules. The probe workflow changes in this commit (SHA bump only), so it runs once more on `v2`; that is one more Savant request and one more MLB request (D16). Every push that touches a workflow with a push trigger (`statcast-probe.yml`, later `daily.yml`) spends real requests, so the commit that changes one says how many; the cap of section 4.4 is a rule of this plan, checked by the reviewer and recorded in STATUS, not enforced by code.

**3.2 What covers `gh` and the REST API (row 2).** The git guard (`.claude/hooks/git_guard.py`) reads `git`. It does not read `gh`, `curl`, `Invoke-RestMethod` or the GitHub API, and the token `gh` uses today is an admin login (`gho_…`) that can edit rulesets, secrets, deploy keys and environments (the rulesets themselves have no bypass actor). Three layers, each stated for what it is:

1. **The hook is extended** (this is a guard against an agent breaking the written rules, not a security boundary; same wording as in `AGENTS.md`). It blocks, in the Bash and PowerShell tools, including the wrappers it already reads: `gh api` with any method other than GET (`-X`/`--method`, or `-f`, `-F`, `--field`, `--raw-field`, `--input`, which turn the call into a POST) on any path; `gh repo` (delete, edit, rename, archive, transfer, deploy-key), `gh secret`, `gh variable`, `gh ruleset`, `gh workflow` (run, enable, disable), `gh run` (rerun, cancel, delete), `gh pr` (merge, close, reopen, edit), `gh release`, `gh label`, `gh auth` (token, refresh, logout, setup-git), `gh extension`, `gh alias`; and `curl`, `wget`, `Invoke-RestMethod`, `Invoke-WebRequest` against `api.github.com` with a non-GET method, a body or an `Authorization` header. Reads stay allowed (`gh run list/view`, `gh api` GET, `gh pr view/list`, `gh repo view`), because the D35 loop needs them to check CI and the rulesets. `AGENTS.md` ("Agency workflow") gets the exact list and the exact limits, as it did for git. Tests in `tests/test_agent_git_guard.py`: one red test per blocked family and one allowed control per read.
2. **A read-only token for agent sessions (owner: yes, G6).** The strongest layer is that the agent's `gh` cannot write at all: the owner creates a fine-grained personal access token limited to this repository with read-only Contents, Actions, Pull requests, Metadata and Administration, and sets it as `GH_TOKEN` in the terminal where Claude Code or Codex runs. `gh` then uses it instead of the admin login, so a missed pattern in layer 1 still fails at GitHub. Cost: the owner keeps the admin login for the release steps in a different terminal. The owner will create it; the hook (layer 1) does not depend on it, so row 2 does not wait for it.
3. **Server-side, what already exists and what this plan adds.** Rulesets protect `main`, `v2` and the tag (they are only as strong as the admin rights of the token in use, so layer 2 is what protects them from an agent). Since 2026-10-21 the `main` ruleset has no "Restrict updates"; its rules are: no deletion, no force push (`non_fast_forward`) and a required pull request (0 approvals, merge method "Merge" only), read with `gh api` on that date (section 13, answer 9). The new `data-publish` environment is restricted to `main`, so the deploy key is not exposed to any other branch, pull request or fork. The only bypass actor of the `main` ruleset is the deploy key (D41), added once by the owner before the first daily run (section 11, G7); a push by the key skips the pull request rule, nothing else does. The CI guard test (3.1) stops a workflow that would use a secret outside that job.

Layers 1, 2 and 3 are all in the plan (G6 answered yes).

## 4. P1.2 — the daily workflow without postgame

**4.1 What it does.** Once a day (and on demand) it asks the MLB schedule for the day's games, builds the live snapshot for up to three games, generates the page's JSON with the rules writer, validates it, and publishes it. No postgame (D41): live matchups already carry `postgame: null` and the workflow already says the postgame was not graded. A run with no games is P1.6.

**4.2 Pieces.**

- `data_pipeline/daily.py` (row 4): `python -m data_pipeline.daily [--date YYYY-MM-DD] --out PATH [--dry-run]`. It runs `run_live_pipeline`, the generator and `validate_payload`, and writes the candidate file to `--out` **only if every step passed**; otherwise it leaves `--out` untouched and exits non-zero with the sanitized `{source, code}` (rule 8). The previous published file is therefore never replaced by a failed run. Exit codes: 0 a valid live file; 1 a failure; 3 is reserved for the valid no-games file of row 9 (P1.6) and is not produced before it. `--dry-run` changes nothing in the repository. `daily.py` reuses `generate_demo_json.build_payload` (which already chooses live data from the processed run record and falls back to the labelled demo) and the existing validation; it adds the orchestration, the `--out` rule and the exit codes. A payload that `build_payload` returns in a fallback mode (`demo_fallback`, `demo_cached`) is never a candidate: the daily job publishes only `live` files, so a live run that failed, or a day with no games before row 9, is exit 1 with the `{source, code}` of the run record (`{pipeline, no_games}`, `{pipeline, no_usable_games}`, ...) and `--out` untouched. After row 9, exit code 3 is a success in the `build` job (green, the summary says "no games"); 1 is red.
- `scripts/publish_data.py` (row 5): takes the candidate file, copies it to `public/data/pitchcraft-demo.json`, and refuses to commit if `git diff --name-only` shows any path outside `public/data/` and `evals/live/` (D15). It commits under the owner's identity, Daniel Herdenez <edherdenez@gmail.com> (owner, question 5; recorded in D42 as the identity of D15's bot commits), with the subject `data: daily update YYYY-MM-DD`, and pushes to `main` with `GIT_SSH_COMMAND` using the deploy key, with strict host-key checking against GitHub's published host keys (pinned in the script, verified against GitHub's documentation at implementation). It skips the commit when the file is unchanged apart from its timestamps. `--dry-run` does everything except the push, in a temporary clone, and prints the file list and the allowlist verdict.
- `.github/workflows/daily.yml` (row 5), two jobs:
  - `build`: any ref, `permissions: contents: read`, no secret. checkout, setup-python, pinned install, restore of the data cache (`actions/cache`, key by run with a prefix `restore-keys`, so closed Savant months are fetched once as D23 says even though the runner is new each day), `python -m data_pipeline.daily`, then `scripts/publish_data.py --dry-run`, then an upload of the candidate as a workflow artifact (retention 7 days) and a step summary (counts, errors as `{source, code}`, never a body).
  - `publish`: `needs: build`, `if: github.ref == 'refs/heads/main' && github.event_name != 'push' && inputs.dry_run != true`, `environment: data-publish`. Downloads the artifact, re-validates it (`python -m data_pipeline.daily --check FILE`, no network), runs `scripts/publish_data.py`. The key is written to a `0600` file in `$RUNNER_TEMP` and removed at the end of the job; it is never echoed.
  - Triggers: `schedule` (one cron per day, time in question 7), `workflow_dispatch` (inputs `dry_run`, `date`), and `push` to `v2` **only when `daily.yml` changes** (the same rule as the probe, so a code push never spends Savant requests). `concurrency: group: daily-data, cancel-in-progress: false`.
- Real publishing happens only from `main` through the environment deploy key, by three independent locks: the environment accepts only `main`, the `if` of the job, and the ruleset bypass belongs to the deploy key alone.

**4.3 Failure behaviour and the exception to rule 5 (decision requested).** `docs/DATA_CONTRACT.md` rule 5 keeps one exception (D34): the Critic's `unsupported` and `validate_payload` stop the whole file and keep the previous one. PLAN asks P1.2 to review it: should the daily job drop only the affected game? Recommendation: **keep the exception for v2.0-a.** Reasons: the snapshot step already drops one unsafe game and publishes the others (F11, D38), so the rule already isolates failures where the data can be judged per game; what reaches `validate_payload` is a defect of the code or of the contract, and publishing a partly checked file during the World Series is the wrong risk; and changing it needs a decision and a change to the contract, with no time to review it. What the job does instead: the previous file stays (the page's own labels say when it was fetched), the job goes red, the summary names the `{source, code}`, and the owner sees a failed run. Revisit after the release. If the owner prefers dropping the game, that is a new decision and a separate commit before the gate.

Timeouts and the missing status check of `pybaseball`: `fetch_pitcher_statcast` guards the `requests` call that `statcast_pitcher` makes, the way the probe did (a patched `HTTPAdapter.send` that sets a 60-second timeout and records the HTTP status), so a request cannot hang and a non-200 answer is a recorded `statcast_pitcher` / `request_failed` source failure. `request_failed` is already in the closed set (`contract_checks.RUN_ERROR_CODES`), so no new code and no new schema version are involved.

**4.4 Request budget (D42, new decision, text proposed).** D23's 210 covers team batting only, D29 the open month. Proposed D42: *The Statcast pitcher fetch (`statcast_pitcher`) is capped at 20 requests per run (up to 5 candidate games, 2 starters each = 10, with margin), sequential with the 2 s pause of D23, and each answer is cached. The pitcher-hand lookup keeps its cap of 10 per run (`PITCHER_HAND_MAX_REQUESTS_PER_RUN`). A run that would exceed the cap records the starter as unavailable with an error and goes on. Closed months of team batting stay fetched once (D23); the data cache is restored between runs so that stays true on a fresh runner. Development dry runs on `v2` are limited to three full runs.* Why 20: a World Series day has one game; the busiest realistic postseason day has four, so 20 is generous without being bulk. The cap becomes a constant tested like `SAVANT_MAX_REQUESTS_PER_RUN`. Expected real requests for the three full dry runs: at most 3 × (20 pitcher + 70 team batting + 10 hand lookups), where 70 is the worst case of 5 candidate games × 2 teams × 7 months before any cache exists; the data cache restores between runs, so only the first run is near that and later ones need far fewer. A cache saved on `v2` is not readable from `main`, so the first run on `main` starts cold (R6 expects it). They are listed in the commit that runs them.

**4.5 Tests for the P1.2 rows.** Row 3: cap enforced (the 21st request raises and is recorded), pacing, cache hit costs nothing. Row 4: a good run writes `--out`; every failure family (schedule failure, no usable game, snapshot mismatch, critic `unsupported`, `validate_payload` failure) leaves `--out` byte-identical and exits non-zero; `--dry-run` writes nothing outside `--out`. Row 5: `publish_data.py` against a local bare repository (file remote) in a temporary directory: commits only the allowed paths, refuses a diff that touches anything else, skips an unchanged file, builds the right message and the owner's identity; no real push is made by a test. The real push with the deploy key can only be proven on `main`, so it is part of the release steps (R6, R7) and is the main residual risk of the plan (section 14).

**4.6 Dry run on `v2` (acceptance).** After row 5 the owner sees, on a push to `v2` that changes `daily.yml`: the `build` job green with a real candidate file validated, the summary, the artifact, `publish` skipped. Nothing is committed. The candidate is downloaded and checked against the served-file tests locally before the first merge.
