# P2.4 side task: D50 cut-offs and D51 versioned cut-off sets

Status: APPROVED by the owner on Oct 30 (owner gate for the schema change). Commit 1 of 2 of this session; commit 2 is gate 4a (`docs/plans/P2.4.md`).

## Why
The D32 recompute (gate 3) moved two lineup cut-offs; the owner approved D50 (K 24.0 / BB 9.0 / OPS .735). Rewriting the bot-owned `public/data/pitchcraft-demo.json` is not allowed (D15) and would not survive, so the stale v2 copy (and, at the release pull request, the daily file on `main`, written under D32) would fail the validator of D50 code: it says ".744 OPS is average".

## What (owner's decision, additive schema 0.10.0, D51)
- `labels.CUTOFF_SETS` (one table keyed by decision id: D32, D50), `CURRENT_CUTOFFS = "D50"`, `HISTORICAL_CUTOFFS = "D32"`, `cutoffs_for(metadata)`: absent field means D32, unknown or malformed id raises `UnknownCutoffs` (fail closed). The agents' constants are the current row.
- New label `metadata.label_cutoffs`; `SCHEMA_VERSION = "0.10.0"`; `READABLE_VERSIONS = ("0.9.0", "0.10.0")`. The validator reads both (0.10.0 requires the field, 0.9.0 has none); the provenance manifest registers the label; the archive carry-forward accepts a 0.9.0 live file as its source; a processed snapshot stays exact-version.
- Rule 4 (`claims_registry`) judges the OPS band and the strikeout/walk notes with the set the file names. `verify_claims` fails closed on an unknown id.
- The generator stamps `labels.CURRENT_CUTOFFS`. `lib/types.ts` gets an optional field; the page does not read it.
- D51 appended to `DECISIONS.md`; `DATA_CONTRACT.md` and `data-inventory.md` updated. No frontend behaviour change (if one were needed, stop and ask).
