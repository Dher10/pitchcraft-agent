## 1. D32 lineup-vs-hand recompute (first, before findings)

D32 is provisional: 23.0% K, 9.0% BB, .750 OPS, inclusive, compared with the displayed figure
(K and BB to one decimal, OPS to three). Method, fixed before any data is read:

- **Population:** 2026 regular season (game type R) through the last regular-season date,
  from the Savant team-batting cache that D23/D29 already define (30 teams x 2 pitcher hands =
  60 team-hand rows). One row per team and hand: plate appearances, K, BB, OPS from the
  same columns the report uses (`k_rate_vs_hand`, `bb_rate_vs_hand`, `ops_vs_hand`).
- **Eligibility:** all 60 rows; a row needs at least 200 plate appearances against that hand,
  otherwise it is excluded and listed. Record each exclusion and its count.
- **Statistic:** the 25th/50th/75th percentiles by linear interpolation (the `numpy` default),
  computed on the unrounded values, then the **75th percentile for K and OPS and for BB**
  rounded as D25 did (K and BB to whole percent; OPS to .005). Both hands are reported
  separately and pooled; the cutoff compared is the pooled one, with the per-hand values disclosed.
- **Provenance:** cache month files, fetch times and SHA-256 digests, the as_of end date, rounding
  rule and the Python/numpy versions, all in `docs/thresholds-proposal.md`.
- **Disclosure:** this is a retrospective calibration on the same season the cases come from, not
  a prospective split. The cases are not used to pick the cutoffs.
- **If the rounded values equal 23.0 / 9.0 / .750:** record "unchanged" with the evidence and
  continue. **If any differs:** do not change `labels.py`. Present the draft decision below.

## 2. Forty stratified cases

- **Strata (mutually exclusive, primary):** ten high-data veterans; ten positive but limited samples;
  ten openers or bullpen-adjacent starts; ten postseason. Priority order for assigning a case with
  overlapping traits: postseason, then opener, then limited, then veteran. Overlapping traits are
  recorded on the case, never hidden.
- **Objective rules (written into `build_dataset.py` and tested; fixed before sampling):**
  - veteran: every labeled dimension clears its D24 sample threshold as of `as_of`, and at least three
    prior MLB seasons. **[amended Oct 29]** The prior-seasons count comes from the MLB `people` year-by-year
    stats, one request per veteran candidate, recorded in the request ledger under `mlb_people` and counted
    inside the 120 MLB ceiling (section 4); no source outside the ledger is used. A count that cannot be read
    is unknown, and an unknown count never qualifies a pitcher as a veteran.
  - limited: at least one pitch/sample dimension is positive but below its D24 threshold (so the report
    must say the sample is small).
  - opener/bullpen: the listed starter averaged under 2.0 innings in his previous starts of the season
    or is flagged as an opener by the schedule data; recorded with the evidence. **[amended Oct 29]** A
    pitcher with no previous start that season has no average, so he is not an opener on the innings test
    (unknown is never zero); he qualifies only if the schedule data flags him, and the case records that
    flag as its evidence. Previous starts are games he started dated before `as_of + 1` (on or before `as_of`).
  - postseason: game type in `POSTSEASON_GAME_TYPES`.
- **Candidate pool and sampling:** pool built from the 2026 schedule, sorted by (official date, game pk).
  Selection is seeded: rank = SHA-256(seed + game pk), seed = SHA-256 of the frozen strata text, recorded
  before the pool is read. Take the first ten eligible per stratum with no two cases sharing a starter or
  a game. Do not fabricate missingness; a stratum that cannot fill ten is reported short, not padded.
- **as_of:** every case uses `as_of = official game date - 1` (D29). The historical builder rejects
  `as_of=None`, and any source row dated on or after the game date.
- **Postseason:** every series standing is computed before first pitch; controls: Game 1 (no prior
  result), a later game (standing excludes that game), and a case where the series ended in that game
  (no final-result leakage). Negative tests seen red before the builder exists (D28).
  **[amended Oct 29]** The 2026 postseason is not assumed complete. At execution time the schedule data
  is read, and only games whose status is final and whose official date is before the collection date are
  eligible. The "series ended in that game" control may come from any completed round. If the stratum cannot
  fill ten, it is reported short.
- **Regression suite (separate):** debut, zero sample, null pitch data, shortened and postponed games.
  Reported apart. Neither set claims accuracy.

## 3. Sealed 20/20 split

- Within each stratum, five cases to dev and five to test by seeded rank (seed recorded before the
  pool is read). That gives a 20-case dev and a 20-case test split, equal per stratum.
- **[amended Oct 29]** The split file is committed with case ids and SHA-256 hashes before any writer-guide
  drafting starts; a test fails if the committed split changes afterwards (`evals/data/split.lock` pins its
  hash).
- The split file lists case ids and hashes only. Packets and findings for both splits are built once and
  frozen with their SHA-256 in the manifest; A, B1 and B2 read the same files, with no refetch.
- **Sealing control (honest scope):** the test split is held on this machine and the repo, so this is a
  process seal, not a cryptographic one. Test outputs, labels and aggregates are never opened or reported
  before the freeze; only hashes are read. A test asserts that no dev tool or report reads test outputs.
  If a stronger seal is wanted (for example storing test packets outside the repo), that is an **[owner]**
  choice.

## 4. MLB and Savant request ledger (no cap evasion)

The per-run constants in `live_pipeline.py` stay as they are: 210 Savant requests in total
(30 teams x 7 monthly chunks, each fetched once and cached), 10 open-month requests per run, 20 pitcher
Statcast requests per run, 10 pitcher-hand requests per run, 2 s pause. Collection runs in batches of at
most five games (one run each). A collection-wide ledger (file under `evals/data/`, hash-chained like the
probe ledger) records every request before it is sent, and the collection stops at these ceilings:

| Source | Per batch | Collection-wide ceiling (8 batches for 40 cases) |
|---|---|---|
| Savant closed-month team batting | shared cache | 210 (D23, once per team-month, never refetched) |
| Savant open-month team batting | 10 | 80 |
| Pitcher hand lookups | 10 | 80 |
| Pitcher Statcast | 20 | 160 |
| MLB schedule/series/standing/people lookups (`mlb_schedule`, `mlb_series`, `mlb_people`) | counted | 120, collection-wide (approved Oct 29) |

Pacing: 2 s between Savant requests, as today. Resumable: a rerun reads the ledger and the caches first;
a cached request costs nothing and is not counted again. A rehearsal run does not count as a fourth daily
rehearsal and none is run outside the approved execution. Each cache record keeps fetch time and a source
digest. Batches that would exceed a ceiling stop with a closed code and partial results are kept.

The D32 recompute (section 1) reuses the closed-month caches above, so it adds no request beyond the 210.

## 5. Hard Gemini call cap (applies to every collection, eval and writer run)

- **Counted unit:** every Gemini HTTP request, including timeouts, retries and fallback calls (D49), counted
  before the request is sent and stored in a durable ledger so a crash cannot undercount.
- **Worst case per item:** two content attempts (initial + informed retry, D2) x (primary, primary retry,
  fallback, fallback retry) = **8 HTTP calls**. Typical expectation is 1 to 2.
- **Run cap (approved Oct 29):** 4 x the items in the run (B1 over 40 cases: 160). **Experiment cap (approved):** 400
  Gemini HTTP calls across B1, B2 and any re-runs, against the 60 required first attempts (60 items would
  take 480 at the 8-call worst case, so the experiment cap stops a runaway rather than allowing it).
  These are limits on calls, not on tokens; Gemini's token and RPM/RPD limits for this project are still
  unpublished and remain AI Studio evidence.
- **At the cap:** the run stops cleanly. The item in flight finishes on the rules writer with the closed
  code `call_cap_reached` and path `rules`; remaining items are recorded as `not_attempted`. Partial
  results, the path counts and the cap state are written to the run summary. A capped run is never
  presented as complete coverage, and a rules or capped result is never a Gemini B1/B2 success.
- **Implementation:** a `CallBudget` used by `agents/writer_policy.py`, with tests: cap reached mid-item,
  cap reached before the first item, resume from the ledger, and the worst-case 8 calls per item.
  This is written with P2.2, not in P2.4, and is noted here so the plan states the numbers.

  short strata reported, not padded; split five/five per stratum.

- Sealing: no dev tool reads test outputs.
- D32 recompute: fixture-based, including the "unchanged" and "changed" outcomes, rounding edges and
  the minimum plate-appearance exclusion.
