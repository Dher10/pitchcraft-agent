### 4.2 Data needed per game, and where it comes from

| Field | Source | Extra request |
|---|---|---|
| `gamePk`, date, teams, venue, round (`gameType`), series name and game number | day schedule (MLB Stats API, already fetched) | none |
| Final score, winner, state | same response (F7) | none |
| Series standing **after** the game, series over | `hydrate=seriesStatus` added to the day request | none (same request) |
| Probable starters | day schedule `probablePitcher` | none |
| **Actual starters**, and each starter's **final line** (innings pitched, hits, earned runs, walks, strikeouts) | game boxscore (first pitcher listed per team; his `stats.pitching`) | 1 per game, **the same request for both: zero extra** |
| The pregame report (pitch data, labels, offense splits, series line) | the existing live pipeline with `as_of = game_date - 1` | see 4.3 |
| Prior MLB seasons of each starter (for the veteran rule) | `gameLog,yearByYear` per pitcher, cached on disk, as `evals/collect_sources.py` already does | 1 per distinct starter |

**Starter check (OWNER, OQ3).** The schedule keeps a probable pitcher for a played game only if MLB still lists one; I have not verified that it persists for all postseason dates, nor that it equals the pitcher who started. R4-D7 measures it on 3 dates. Rule proposed: a report is shown only when the boxscore confirms both probable starters started; when one did not, the page shows the report with the explicit line "probable starter {name}; {name} started" taken from the boxscore (a source value). The alternative is to hide the report and show the result only. A game whose boxscore cannot be read keeps `starters_check: unknown` and says so.

**Final line (owner's answer to OQ14).** The page shows each actual starter's line exactly as the boxscore gives it: innings pitched, hits, earned runs, walks, strikeouts, labeled "Final line". Source values only: no grade, no Game Score, no verdict, no comparison with the report (D41's cut of automated grading stands). A field the boxscore does not give is `null` and shown as unavailable, never 0; a real 0 is a measured zero. The line belongs to the pitcher who started, so when the probable starter did not start it is the line of the one who did, with his name.

**What is not fetched:** grades, win probability, play-by-play, relievers. Nothing about what happened in the game is shown except the final score, the series standing after the game and the two final lines.

### 4.3 Request budget (D16)

All of these are **past games, fetched once, cached on disk**, and resumed from the cache; the five published reports cost nothing. Numbers are my count from the code's calls per game; **R4-D4 turns them into constants with tests and R4-D7 measures them**, so treat the table as the proposal for D66, not as measured.

Unit counts: dates D = 34 (2026-09-28 to 10-31), games G <= 53 (planning figure about 45 to 50; the five published ones are excluded from Savant and series requests), distinct starters P <= 106 (planning about 85), teams T = 12.

| Source | Call | Per unit | Ceiling | Planning |
|---|---|---|---|---|
| MLB Stats API | day schedule (with `probablePitcher`, venue, `seriesStatus`) | 1 per date | 34 | 31 |
| MLB Stats API | boxscore (actual starters **and their final lines**; no extra request) | 1 per game | 53 | 45 |
| MLB Stats API | series status before the game (`fetch_series_status`, none for game 1 of a series) | up to 2 per game | 106 | 80 |
| MLB Stats API | `gameLog,yearByYear` per starter (season line as of the game, prior seasons) | 1 per starter | 106 | 85 |
| MLB Stats API | pitcher hand when a frame lacks it | new ceiling 20 (code and D42 today: 10) | 20 | 5 |
| **MLB total** | | | **319** | **about 245** |
| Savant | `statcast_pitcher` frame per starter per game | 2 per game | 106 | 90 |
| Savant | team batting, closed months (Mar 25 to Sep) | T x 7 | 84 | 84 |
| **Savant total** | | | **190** | **about 175** |
| **Both** | | | **509** | **about 420** |

- **Team batting needs no per-game request.** `fetch_team_splits` asks Savant for the batting side of a team from opening day through `min(as_of, last day of the regular season)` (`live_pipeline.py`, `fetch_team_splits` and `fetch_team_batting_statcast`: regular season only, `hfGT=R`). For every postseason game that window is the same, 2026-03-25 to 2026-09-27, so each of the 12 teams costs 7 monthly requests once (the last chunk ends at the season end and counts as closed) and every later game of the team is a cache hit. The lineup splits of a postseason report are therefore **regular-season splits through 2026-09-27**, as in the five published reports; the page must say so through the scope that the pipeline already writes (section 4.4, rule 3).
- **Counters, a note:** the counters of R4-D4 are per run of the backfill, not the daily ones: the pitcher frames get a ceiling of 106 (the daily cap is 20, D42), team batting 84 (D23's 210 is for the whole season of 30 teams) and the MLB total counts every HTTP request, including the one `/seasons` call the calendar makes, so R4-D7 may show 320 against the 319 of the table; the ceilings are set with that margin in R4-D4.
- **Pacing and time:** Savant keeps the 2 s pause of D23 (about 6 minutes for 190 requests); MLB requests get a 0.5 s pause in this run. Estimate: 15 to 30 minutes. Workflow timeout 90 minutes; the cache is saved even on failure so the run resumes.
- **Ceilings are hard.** Each source has its own counter at the HTTP layer, like `_counted_pitcher_transport`; past the ceiling the run stops with exit code 1 and a closed code, it never writes a game built on a missing request, and the games already built stay.
- **A cheaper option (OWNER, OQ4), small.** The 106 per-game Statcast pitcher frames could be replaced by one frame per starter through the last postseason date, sliced locally by `as_of`: about 85 requests instead of 106, a saving of about 20. It needs a slicing function with the same strict `as_of` tests and changes the cache key of the pitcher fetch, so it is more code and more risk for a small saving. My recommendation: **do not do it**; build with the existing per-game calls (the code that produced the published reports, so all games are comparable) and measure in R4-D7.
- **Why this is inside D16** (the proposal for the owner to judge): non-commercial, attributed, cached, paced, a single one-time run for past games, resumable without repeating requests. It is of the same order as the P2.4 collection (134 MLB requests and the Savant ceiling of 210 of D23). It is **not** a bulk download of a season; a later season-wide extension needs its own decision.
- **Series line, a note:** the standing before a game could also be derived at zero requests from the day schedules already fetched (each game's `seriesStatus` after it). I keep the existing function because it produced the published reports and its provenance is already in the manifest; this is the smallest saving and the smallest risk to give up.
- **Daily job after R4:** unchanged (D42 caps stay). Several games per day and the daily job writing game files are P1.3 and 2027 readiness.

### 4.4 Static data layout, schema and contract impact

```
public/data/
  pitchcraft-demo.json              unchanged: the daily file, bot-owned (D15), schema 0.10.0
  archive/
    manifest.json                   version, season list, counts, SHA-256 of index and of every game file
    index-2026.json                 one row per game played, with the notable tags
    games/<gamePk>.json             one file per game: envelope + one-matchup payload
```

- **Id.** The route and file id is the MLB `gamePk` (a public integer), validated by `^[1-9][0-9]{5,8}$` before any file is touched. Flat directory: a `gamePk` is unique across seasons. No path is ever built from raw input.
- **Game file.** Compact JSON (no pretty printing: 25.7 KB against 48.6 KB). Shape (the values are **illustrative**, not a real game):

```
{
  "archive_version": "1.0.0",
  "game_pk": 849823, "season": 2026, "date": "2026-10-04",
  "round": "Division Series",                       // from gameType, closed table
  "result": { "status": "final", "away": {"abbreviation": "LAD", "runs": 4},
              "home": {"abbreviation": "CIN", "runs": 0}, "winner": "away",
              "series_after": "LAD leads 2-0", "series_over": false },
  "origin": { "kind": "reconstructed" | "published_live",
              "as_of": "2026-10-03", "built_at": "<instant>", "published_at": "<instant>" | null },
  "starters_check": { "away": "started" | "did_not_start" | "unknown", "home": "...",
                      "actual": { "away": {"id": 1, "name": "<name>"} | null, "home": {...} | null } },
  "final_line": { "away": {"innings_pitched": "6.1", "hits": 4, "earned_runs": 1, "walks": 2, "strikeouts": 7} | null,
                  "home": {...} | null },     // each field null when the boxscore gives none; the whole line null when unknown
  "payload": { ...a full schema 0.10.0 payload with one matchup, as the daily file... }
}
```

  The payload is the one the pipeline wrote: schema 0.10.0 for a reconstructed report and the file as published (0.9.0, cut-off set D32) for the five `published_live` ones; the validator reads both (R9). Embedding the **same payload** the daily file has means `validate_payload`, `check_contract`, the provenance manifest, the claims registry and the page components all apply unchanged, and a published report (`published_live`) is copied without being rewritten. `payload.metadata.data_fetched_at` is the real instant of the fetch; for a `reconstructed` report it is later than the game, and the page must not call it "published" (rule 7).
- **Index row** (about 0.5 KB; a 2,700-game season is about 1.3 MB, so one file per season; sharding by month stays possible because readers go through one function):

```
{ "game_pk", "date", "season", "round", "series": {"name","game_number","games_in_series"},
  "away": {"abbreviation","name"}, "home": {...}, "status": "final",
  "result": {"away_runs","home_runs","winner"},
  "starters": {"away":"<name>","home":"<name>"},
  "report": {"origin","as_of","starters_check"},
  "notable": ["series_clincher","strikeout_duel","veteran_duel"] }
```

  Only games that were **played** are indexed; a postponed or suspended game has no result and no row.
- **Version.** The daily file stays **0.10.0**: R4 adds no field to it. The archive family has its own version, `archive_version 1.0.0`, with its own reader check by equality as D36 does: a file of another version is not read. This is a new file family and a new version, so it is **a decision for the owner (D66, OQ12)**. The TypeScript types gain `ArchiveGame` and `ArchiveIndexRow`; `PitchCraftData` is untouched.
- **How each rule of the contract applies (text to add in R4-D2):**
  1. *Provenance.* `result` is a source value (the schedule); `final_line` and `starters_check.actual` are source values (the boxscore); `origin`, `as_of`, `built_at`, `starters_check` are documented derivations; `notable` is a derivation by the rules of 4.6; `round` is a closed table from `gameType`. Added to the manifest of `provenance.py`.
  2. *Unknown is never zero.* A score is a number only for a final game; a final-line field the boxscore does not give is `null`, a real 0 stays 0, and a line is never taken from a pitcher who did not start; a missing boxscore is `unknown`, never "started"; a missing label never makes a tag.
  3. *Scope.* The report keeps the scopes the pipeline already writes: pitch figures through `as_of`, and the lineup splits **regular season through 2026-09-27** for every postseason game (the fetch never goes past the regular season). The result is a different thing from the report and is labeled as the final score; nothing the report says covers the game itself.
  4. *Claims.* Every text the new pages write about data is a catalog phrase with a registry condition: the origin line, each notable reason, the starter note, the result line. Each reason is registered with the condition that produces it, so the page can never print a reason the data does not support.
  5. *Isolated failure.* **A change to rule 5, part of D66 (OWNER, OQ12).** Rule 5's exception (D34, kept by D42) stops the whole file when the critic says `unsupported` or `validate_payload` fails, and keeps the previous file. In the daily job that is one file per day. In the backfill the unit is a game and every game is its own public file: a game that fails validation or the critic is **not written** and is recorded with a closed code, and the other games are published. The integrity gate is unchanged (nothing that fails reaches any public file); only its scope shrinks from the whole run to the one game file. The index lists only games whose file exists and validates. Test: a game forced to fail leaves no file and no index row while its neighbors are written.
  6. *Honest mode.* The origin is stated on every game page; there is no demo content in an archive file.
  7. *Real state and time.* `status` follows `schema.GAME_STATUS`; the words "published", "today" and "before first pitch" appear only where the data supports them (a reconstructed report is "written after the game, from data through {as_of}").
  8. *No internals.* The failure of a game or the `starters_check` carries closed codes, never exception text. New codes proposed (D66): `game_not_found`, `starter_unconfirmed`, `ceiling_reached`.
- **Archive and the daily file's `archive[]`.** The home page's Archive section will read the **index** (with results). The daily file's `archive[]` keeps its current shape and validation (`result_label` null) and is left alone in R4; retiring it is a later cleanup (OQ8).

### 4.6 "Notable duels of 2026": the criteria

Fixed, written down before any data is read, shown on the page next to each game as its **reasons**. The candidate pool is every **postseason game played** with a report. A game is notable when it has **at least one** of the four reasons below (owner's answer to OQ5).

| Reason key | Rule | Data |
|---|---|---|
| `series_clincher` | The game ended its series: after it `series_over` is true (the winner reached the wins the series needs). | `seriesStatus` after the game |
| `strikeout_duel` | **Both** starters have the strikeout label "Above-average swing-and-miss ability" (D25: K% of 25% or more), with the strikeout sample not limited (D24: 70 batters faced), as of the day before. | the report's own labels (`pitching_profile`, `sample.limited`) |
| `veteran_duel` | **Both** starters have at least **V** prior MLB seasons. **V is not fixed here**: R4-D7 reports the distribution among 2026 postseason starters and the owner approves V (proposal: 5), the way D25 set the bands from data first. Until V is approved the tag is not computed and the code refuses to publish the index. | `yearByYear` per starter |
| `world_series` | The game is a World Series game that was played (`gameType` W, status final). Every such game is notable. Phrase: "World Series game". | `gameType` |

- The **round** (Wild Card, Division, League Championship, World Series) is always shown; only the World Series is a reason by itself (`world_series`), because every game in the pool is postseason and the other rounds would qualify all of them.
- **Order:** more reasons first, then the later date first. No score, no weighting, no hidden model.
- **Target size:** measured in R4-D7. If the rule qualifies more than about 40% of the pool, I report it and the owner decides whether to tighten; I do not tune it silently.
- **Computed by code, not by a model, from stored facts**, stored as tags in the index and recomputable from the game files alone. The reasons printed are catalog phrases with registry conditions (rule 4).
- **Not criteria:** who won, run margin, star names, or anything about a prediction (PRD out of scope).
- Unknown inputs yield no tag (a game whose starter label is missing is not a strikeout duel).

### 5.4 Archive and filters behavior

- Filters: **team** (a native select of the teams present in the index, matching either side of the game) and **date** (from and to, bounded by the first and last date of the index). A "Clear filters" action and a visible count ("Showing n of N games").

## 7. Tests

**Data part (pytest)**

- Identity: a published report is matched to exactly one scheduled game; ambiguity or no match is refused (controls: two games the same day, two teams swapped, a starter changed).
- Results: score numeric only for `final`; postponed, suspended and cancelled give no result and no row; a tie-breaking edge (suspended game completed on a later date) is a named case.
- Leakage: no figure of a report dated on or after the game day; `as_of = game_date - 1` for every reconstructed game (D29); a frame with a row on the game date still produces no figure from it.
- Ceilings: each source stops at its ceiling (control: ceiling minus one passes); counters count only HTTP requests, a cache hit costs nothing; resume skips an existing valid file and rebuilds a corrupt one.
- Starter check: started, did_not_start, unknown (boxscore missing) each give the right state; unknown is never "started".
- Final line: each field copied from the boxscore of the pitcher who started; a missing field is `null`, a real 0 stays 0 (control for both); a line is never taken from a reliever or from the probable starter who did not start; no grade or derived figure in the file; the boxscore is requested once per game and that one request supplies the starters and the lines (counter test: zero extra requests).
- File and index: validators accept a good game file and refuse each mutated field (one negative test per field and per closed code); index equals the game files; manifest equals the files present; `archive_version` mismatch refused.
- Notable: each reason (including `world_series`: a game of another round or not final never gets it) has a positive case and a control that fails if a condition is weakened (a limited strikeout sample, a label that is average, one veteran starter, a series not over, a missing field); ordering is deterministic.
- Contract: the registry test (every new phrase registered, registry equals the contract table), the manifest test for new paths, the no-tolerance guard.
- Publication: the script commits only under `public/data/`; a path outside is refused and the work tree restored; unchanged content yields no commit; subject and identity as D42.
- D15 guard: a test (or CI step) that fails if a commit of the plan touches `public/data` or `evals/live`.
- Sealed-set guard: R4 modules import nothing from `evals/` and read no path under `evals/data/dataset/packets`, `.local/` or the labels.

**UI part (vitest + a browser check)**

- Readers: id pattern, missing file, wrong version, index missing.
- Archive: results shown; Grade column absent when no row has a grade and present when one does; rows are links; phone layout has no horizontal scroll (browser check at 375 and 1280 px).
- Game page: each state of 5.2, the origin line for both origins, the starter note, 404 for unknown and invalid ids.
- Notable: reasons rendered from the tags only; empty state.
- Filters: URL parsing (valid, invalid, out of range, injection-looking strings), team matches either side, date bounds inclusive, pagination, empty result, clear.
- Accessibility: labels on controls, keyboard operation, focus visible, status messages announced, no color-only signal (the audit found several).
- Analytics: the existing component test still passes; no custom event added.
- Production-like check: `next build --webpack` locally (QA3-02: the Turbopack build panics on Windows PostCSS), the five suites, then a Vercel preview: a game page loads its JSON in the function (risk R3).
