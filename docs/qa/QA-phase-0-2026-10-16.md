### QA5-01 — a sixth pitch becomes a false zero

**Expected:** every published count/share reflects the source. Omitting a pitch from a display selection cannot prove that the starter never threw it. D34 rules 1 and 2 apply to unrendered JSON too.

**Actual:** `process_pitcher_statcast` constructs the complete mix and truncates it with `pitch_mix = pitch_mix[:5]` at line 1471. `_combine_pitch_mix` builds its lookup from that truncated list. If the opponent's list includes the omitted pitch, `not_thrown` fills the first starter's cell with zero counts and shares. The public chart says he threw none; his detail panel also excludes the pitch.

Probe A uses six mapped types for the away starter and an opponent whose primary pitch is the away starter's sixth pitch. It runs the real processor, sample builder, merger, generator and validator:

```text
validated: True
contract violations: []
source FC pitches: 10
published Cutter: {'pitch': 'Cutter',
 'away_starter': {'overall': 0, 'vs_lhh': 0, 'vs_rhh': 0, 'count': 0, 'total': 1150},
 'home_starter': {'overall': 66.7, 'vs_lhh': 66.7, 'vs_rhh': 66.7, 'count': 600, 'total': 900}}
```

This is wrong data that can reach the public site, with no contract violation detected. The expected away count is 10 and overall share is 0.9%, not zero. The frozen inventory's description of a top-five union is not a specification permitting false values.

**Reproduce:** run probe A below. **Smallest suggested fix:** retain all source counts/shares for merging, even if display rows are selected from the top five. Add an asymmetric six-type regression and a source-to-payload conservation check.

### QA5-02 — unknown or unusable events are treated as measured data

**Expected:** a column that cannot identify outcomes yields unavailable figures and a recorded source error. Unknown values must not be classified as ordinary plate appearances or outs. D34 rules 1–2, `ENGINEERING.md` section 1, and P0.15-D2.2 require a usable source boundary; the Gherkin failure scenario covers explicit failures.

**Actual:** `_plate_appearance_events` drops nulls and excludes `NON_PA_EVENTS`, but accepts any other string. `_split_line` includes those strings in its denominators while their hit, walk and strikeout contributions default to zero. `derive_team_splits` uses the same permissive exclusion. On the team path an entirely null `events` column produces `{}` without any error.

Probe C runs `run_live_pipeline → build_payload → validate_payload` with 200 otherwise valid team rows:

```text
null VALIDATED run= ok errors= []
offense= {'summary_label': None, 'vs_pitcher_hand': 'RHP',
 'ops_vs_hand': None, 'k_rate_vs_hand': None, 'bb_rate_vs_hand': None,
 'recent_form': None, 'scope': None}
unknown VALIDATED run= ok errors= []
offense= {'summary_label': 'Real season split vs RHP', 'vs_pitcher_hand': 'RHP',
 'ops_vs_hand': '.000', 'k_rate_vs_hand': '0.0%', 'bb_rate_vs_hand': '0.0%',
 'recent_form': 'Season split',
 'scope': {'kind': 'regular_season', 'through': '2026-07-03',
           'label': 'regular season through 2026-07-03'}}
```

The unknown value is `provider_error`, a deliberately malformed source value. It is not evidence of 200 outs, zero walks or zero strikeouts. The unavailable variant is safe numerically but fails to record the unusable column. A sweep found the same unknown-value acceptance in pitcher `_plate_appearance_events`; the fetcher audit also reproduced false Statcast counts and rate labels when the API has no line.

**Reproduce:** probe C. **Smallest suggested fix:** validate completed-event values through a shared explicit mapping for pitcher and team paths, recording unusable/unknown columns before deriving figures. Preserve legitimate non-PA/null pitch rows and valid empty answers.

### QA5-03 — non-finite measurements pass the integrity gate

**Expected:** unusable measurements cannot reach the public file as numbers. Processing must preserve explicit unavailable states or reject malformed input, and publication must produce valid JSON. D34 rules 1–2 and the P0.12/P0.15 boundary and fail-closed publication tasks apply.

**Actual:** mean/median processing accepts infinity. `pd.isna(inf)` is false. The manifest accepts numeric movement by type, and its velocity check does not exclude infinity. `generate_demo_json.main` serializes with ordinary `json.dumps`, whose default permits `Infinity`; the frontend reader uses `JSON.parse` in `lib/data.ts:10`, which rejects it. Infinite plate locations are instead clipped to a valid-looking edge of the chart.

Probe B passes each malformed column through the real pitcher fetcher, generator and `validate_payload`:

```text
pfx_x validation_failures= 0 errors= [] strict_json= Out of range float values are not JSON compliant: inf
release_speed validation_failures= 0 errors= [] strict_json= Out of range float values are not JSON compliant: inf
plate_x validation_failures= 0 errors= [] strict_json= PASS
locations= [{'pitch': 'Four-seam', 'x': 1.0, 'y': 0.556}]
```

The strict serialization in the probe is a diagnostic only; production serialization does not use it. This review does not claim MLB currently sends infinity. It establishes that malformed numeric source data passes the claimed integrity boundary, can write an unreadable public file, and can also become false coordinates without an error.

**Reproduce:** probe B. **Smallest suggested fix:** validate finite measurements before aggregation/clipping, contain failure in the affected figure, require finite numbers in publication checks, and serialize with `allow_nan=False` as a final guard.

### QA5-04 — frontend movement prose escapes the claims contract

**Expected:** D34 rule 4 covers UI sentences as well as agent text. Each factual sentence needs a documented condition and a test of that condition. The contract's section 3.3 does not register the factual descriptions emitted by `describePitchMovement`.

**Actual:** the frontend invents qualitative/comparative descriptions from insufficient inputs. Direct execution of the real TypeScript function, probe E, prints:

```text
{"family":"Breaking","velocity":85,"hBreak":5,"vBreak":-7}
-> Sweeps arm-side across the zone more than it dives, making the barrel chase sideways.
{"family":"Offspeed","velocity":"N/A","hBreak":0,"vBreak":0}
-> Changes speed more than shape, giving the hitter a timing problem after seeing harder pitches.
```

The first comparison says horizontal movement exceeds drop although the published magnitudes are 5 and 7 inches. The second claims a speed change and a comparison with harder pitches without any measured velocity or comparison pitch. `DetailedAnalysis` calls this function whenever movement is available and the arsenal sample is healthy, including when velocity is unavailable.

There is also a direction dependency missing at line 19: signed `hBreak` determines “arm-side”/“glove-side” without the starter's hand. The source processor copies signed `pfx_x * 12`, without hand normalization. An SSR probe gave the identical “Runs arm-side…” sentence for L, R and S starters with identical signed movement. Opposite throwing hands cannot share the same arm-side direction in a fixed coordinate system. This is an inference from the code's inputs, not a new measurement of Savant coordinates.

The same SSR probe confirmed `Displayed unmeasured speed comparison: true`. These sentences are outside catalog/registry checking; passing payload validation cannot protect them. Existing frontend tests test whether descriptions appear, not whether these facts hold. The missing registry conditions make this a High verification/contract gap independently of the individual copy examples.

**Reproduce:** probe E; follow the call at `DetailedAnalysis.tsx:144`, or run the SSR variant in probe F. **Smallest suggested fix:** register these factual UI phrases with sufficient measurable conditions, use known hand for direction, and remove/suppress unsupported comparisons and hitter-effect claims. Test the false-condition cases, including missing velocity and horizontal movement smaller than vertical movement.
