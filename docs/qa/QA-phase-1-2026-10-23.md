### QA1-01 — opening-series claim ignores the current game state

The analyst emits the opening sentence whenever `series.game_number == 1`. Its registry checks the number and name but never requires an upcoming game. `agents/messages_en.py:141` supplies the present-tense statement. A completed or in-progress Game 1 therefore publishes a false factual sentence in the public JSON. The current page omits that summary body, but D34 explicitly covers unrendered JSON.

Reproduced with `python "$env:TEMP/pitchcraft-series-qa.py"`, using the real mocked pipeline, generator, critic, validator and contract:

```python
from dataclasses import replace
from tests.matrix import HARD_CASES, run_scenario

result = run_scenario(replace(
    HARD_CASES["series_opening"],
    name="qa-temporal", state=("Final", "Final"),
))
# Repeat with state=("Live", "In Progress").
```

```text
series_opening ('Live', 'In Progress') status= live failed= [] violations= []
This is Game 1 of the World Series; the series has not started.
series_opening ('Final', 'Final') status= final failed= [] violations= []
This is Game 1 of the World Series; the series has not started.
```

Expected: claims match the schedule state, including when the daily job runs after play starts or the owner builds an earlier date. Actual: false present-tense claim reaches a valid live payload. Violates D34 contract rules 4/7 and the state-honesty requirement of D40; approved sentence wording does not remove its truth condition.

The same state cross-product for `series_standing` emits “Before first pitch, BOS leads 2-0.” with no violation. That can be a historically correct standing; this audit does **not** claim the standing leaked a result. The phrase nevertheless needs consistent treatment under the literal state restriction at `DATA_CONTRACT.md:116`.

Smallest fix: gate the opening sentence and its registry condition on the upcoming state; cover upcoming/live/final/null states for both series claims. Clarify or gate the later-game wording consistently with the contract. Existing series hard cases exercise Preview and miss this cross-product.

### QA1-02 — equals-form token flag passes the guard

`_gh_problem` recognizes the exact long token `--show-token` and short flags containing `t`, but misses `--show-token=true` and `--show-token=True`. These are accepted Boolean spellings of the installed CLI's token-printing option.

Safe reproduction: import the hook, give `decide` a fake git reader, and evaluate command strings only. **Do not execute a token-display command against a real login.**

```python
import importlib.util
s = importlib.util.spec_from_file_location("qa_guard", ".claude/hooks/git_guard.py")
g = importlib.util.module_from_spec(s)
s.loader.exec_module(g)
for command in ("gh auth status --show-token=true",
                "gh auth status --show-token=True",
                "gh auth status --show-token"):
    print(repr(command), "=>", repr(g.decide(command, lambda *args: "")))
```

```text
'gh auth status --show-token=true' => None
'gh auth status --show-token=True' => None
'gh auth status --show-token' => 'gh auth status --show-token prints the token and is not allowed (P1.0)'
```

`gh auth status --show-token=true --help` exits 0 and documents `-t, --show-token: Display the auth token`; the reviewer also confirmed invalid Boolean syntax is rejected with `strconv.ParseBool`. Help was used without displaying an actual token. No real leak is asserted.

Expected: all equivalent token-printing spellings are blocked. Actual: an ordinary command in an authenticated agent session can print its secret. A read-only token limits writes but is still a secret. This is a realistic security weakness, contradicting P1 row 2, `AGENTS.md:69`, and the prohibition against printing credentials. Existing tests at `tests/test_agent_git_guard.py:735` cover the bare long and short variants only.

Smallest fix: normalize the long-option name and Boolean value before judging it; add equals-form regression cases, including true/false spellings and the documented controls.

### QA1-06 — some post-copy failures leave the checkout changed

`_work_in` copies the candidate before querying status and staging. Its rollback covers allowlist rejection and nonzero commit results, but not a failed `git add`, a status failure after copying, or process/file I/O exceptions. `main` catches only `Failure`.

The same scratch probe used a real fixture `.git/index.lock`, then separately injected a synthetic process-creation `OSError` at git-add. Every push was mocked:

```text
ADD_LOCK_STATUS M public/data/pitchcraft-demo.json
PUSH_MOCK_CALLS 0
PROCESS_RAISED OSError synthetic process creation failure
PROCESS_RESTORED False
```

Expected: the failure contract is explicit and cleanup is consistent. Actual: the first case returns the closed error but leaves the copied target; the second escapes `main` with a traceback. Reproduce in a clean temporary fixture checkout by creating `.git/index.lock` before invoking `main`, or mocking its git-add process creation to raise. This does **not** replace the public remote on failure: the present job uses disposable checkouts and no push occurs in these cases. A rejected push likewise intentionally leaves only a local unpushed commit and fails the job.

Smallest fix: cover copy/status/add/commit with common rollback and map operational exceptions to a closed failure. Add failure-injection tests at those boundaries.
